# Система геймификации операторов

Бэкенд на FastAPI и веб-интерфейс на React, реализующие ТЗ «Система геймификации
операторов» v1.0: внутренняя валюта (коины), личный кабинет, рейтинговая таблица,
магазин бонусов и административная панель.

Реализован полный объём MVP (п. 6.1 ТЗ), включая «желательные» пункты —
номинации недели и экспорт в CSV.

## Быстрый старт

```bash
python -m venv .venv
.venv/Scripts/activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt   # для прода: requirements.txt

cp .env.example .env            # и обязательно поменяйте SECRET_KEY

# демо-данные: группы, персонал, 12 операторов, 3 недели, 2 из них закрыты
python -m scripts.seed_demo

uvicorn app.main:app --reload
```

Интерфейс запускается отдельным процессом (в разработке ходит на бэкенд
через прокси Vite, поэтому CORS настраивать не нужно):

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

- Интерфейс — <http://localhost:5173>
- Swagger UI — <http://127.0.0.1:8000/docs>
- ReDoc — <http://127.0.0.1:8000/redoc>
- Проверка живости — <http://127.0.0.1:8000/health>

Учётные записи после `seed_demo` (пароль `demo12345`):

| Логин | Роль |
|---|---|
| `op01` … `op12` | операторы |
| `sv1`, `sv2` | супервайзеры |
| `head` | руководитель |
| `admin` | администратор (пароль из `BOOTSTRAP_ADMIN_PASSWORD`) |

Проверить вход и получить токен:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/login \
  -d "username=op01&password=demo12345"
```

  services/        бизнес-логика: коины, расчёт недели, магазин, бейджи, отчёты

  scheduler.py     еженедельная фоновая задача (APScheduler)
  main.py          сборка приложения и жизненный цикл

  src/api/         типизированный клиент API, JWT и обновление токена
  src/auth/        контекст авторизации и экран входа
  src/components/  общие элементы: карточки, плитки, таблицы, диалоги
  src/pages/       экраны: кабинет, рейтинг, магазин, админ-панель
  src/styles/      дизайн-токены и оформление
alembic/           миграции схемы
scripts/           демо-данные и закрытие недели из консоли
tests/             юнит- и интеграционные тесты

Слои разделены строго: роутеры не содержат бизнес-логики, сервисы не знают про HTTP,
модели не знают ни про то, ни про другое. Так правила начисления можно тестировать
и переиспользовать (например, в задаче планировщика) без поднятия приложения.

## Интерфейс

React + Vite + TypeScript, светлая корпоративная тема, десктоп в приоритете
с корректным сжатием до телефона. Состоянием сервера управляет TanStack Query,
маршрутизацией — React Router. Оформление собственное: дизайн-токены в
[frontend/src/styles/tokens.css](frontend/src/styles/tokens.css), без CSS-фреймворка.

| Экран | Что показывает |
|---|---|
| Кабинет | баланс, показатели недели с прогресс-барами, из чего сложатся коины, достижения, история операций с фильтрами |
| Рейтинг | пьедестал, номинации недели, общая таблица с динамикой и подсветкой своей строки |
| Магазин | каталог с ценами и «нужно ещё N коинов», покупка с подтверждением, мои заявки |
| Операторы | сводка, таблица с антипоказателями, ручное начисление, выгрузка CSV |
| Заявки | очередь со статусами, одобрение и отклонение с обязательной причиной |

### Дизайн-система Puls

Реализована по отдельному документу «Design Specification 1.0»: содержание —
основной слой, навигация плавает над ним, стекло применяется избирательно.

| Слой | Где живёт |
|---|---|
| Токены | [tokens.css](frontend/src/styles/tokens.css) — цвет, типографика, отступы, радиусы, движение, стекло |
| Стекло | [GlassSurface](frontend/src/components/GlassSurface.tsx) — единственное место с `backdrop-filter` |
| Компоненты | [ui.tsx](frontend/src/components/ui.tsx), [Sheet](frontend/src/components/Sheet.tsx), [icons](frontend/src/components/icons.tsx) |
| Темы | [ThemeContext](frontend/src/theme/ThemeContext.tsx) — Light / Dark / System |

- **Стекло избирательно.** Всего три стеклянных элемента на экран: сайдбар,
  панель фильтров, нижняя навигация. Карточки, KPI и таблицы — обычные
  непрозрачные поверхности. Есть fallback: без поддержки `backdrop-filter`
  или при `prefers-reduced-transparency` стекло становится непрозрачным.
- **Одна ведущая цифра на экран** — баланс коинов; остальные числа мельче.
- **Тема определяется до первой отрисовки** скриптом в `index.html`, поэтому
  тёмный интерфейс не мигает белым при загрузке.
- **Мобильный** получает плавающую нижнюю навигацию, которая ужимается при
  прокрутке вниз, шторки вместо модальных окон и списки карточек вместо таблиц.
  Учтены `safe-area-inset` для чёлки и домашнего индикатора.

### Доступность

Палитра прогнана через валидатор контраста и различимости при дальтонизме.
Проверка показала, что зелёный и красный при дейтеранопии почти неразличимы
(ΔE 4.1), поэтому **цвет нигде не является единственным носителем смысла**:

- динамика места — стрелка ▲▼ **и** знак числа, не только цвет;
- антипоказатели — значок ✓ или **!** и подпись «Нарушений нет» / «Штраф −5»;
- своя строка в рейтинге — фон, полоса слева **и** метка «это вы»;
- места на пьедестале — цвет медали **и** крупная цифра места;
- всплывающие сообщения — значок ✓ / **!** рядом с текстом.

Контраст текста измерен на реальной отрисовке: 40 пар «текст на подложке»
в обеих темах проходят WCAG AA. При `prefers-reduced-motion` анимации
отключаются, зоны нажатия на телефоне не меньше 44×44.

> **Расхождение со спецификацией.** Документ задаёт `--text-tertiary: #9298a5`
> (п. 8), но на белом это 2.89:1 при норме 4.5:1 из п. 200 и 256. Информативный
> текст переведён на проходящий оттенок, а исходный светлый сохранён отдельным
> токеном `--text-quaternary` для декоративных элементов, где контраст не нужен.

Крупная цифра на экране ровно одна — баланс коинов; остальные числа заметно
мельче, чтобы взгляд цеплялся за главное.

### Что учтено в клиенте

- **Обновление токена.** Просроченный access-токен обновляется молча, запрос
  повторяется один раз; при неудаче пользователь возвращается на экран входа.
- **Холодный старт.** Если вход длится дольше четырёх секунд, появляется
  подсказка про пробуждение сервиса на бесплатном тарифе.
- **Резерв коинов** виден отдельно от баланса — оператор понимает, почему
  доступная сумма меньше.
- **Ошибки API** показываются текстом от бэкенда: «Недостаточно коинов: нужно
  120, доступно 45» вместо кода ответа.

## Модель данных

| Таблица | Назначение |
|---|---|
| `users`, `groups` | операторы, супервайзеры, руководители; группы с закреплённым супервайзером |
| `coin_accounts` | баланс, резерв, суммы «всего начислено / потрачено» |
| `coin_transactions` | **неизменяемый журнал** всех операций с коинами |
| `contest_weeks` | отчётные недели (ISO-год + ISO-неделя) со статусом и снимком правил |
| `metric_definitions` | настраиваемые показатели конкурса и антипоказатели |
| `operator_week_metrics` | фактические значения показателей за неделю |
| `operator_week_results` | итог недели: баллы, место, динамика, разбивка коинов |
| `nomination_definitions`, `nomination_winners` | номинации недели и их победители |
| `shop_items`, `shop_requests` | каталог бонусов и заявки со статусами |
| `badge_definitions`, `user_badges` | бейджи и факты их выдачи |
| `gamification_settings` | курс перевода, размеры бонусов, лимиты (единственная строка) |
| `audit_log` | **неизменяемый журнал** действий персонала |

### Баланс и журнал

Источник истины — `coin_transactions`. `coin_accounts` хранит агрегаты, чтобы не
суммировать всю историю на каждый запрос; обе таблицы обновляются в одной
транзакции внутри `app/services/coins.py` — единственного модуля, которому
разрешено менять баланс.

Инварианты счёта: `balance >= 0` и `0 <= reserved <= balance`. Доступные к трате
коины — это `balance - reserved`.

### Неизменяемость истории

Требование п. 5 ТЗ («операции хранятся бессрочно и не могут быть удалены»)
обеспечивается на уровне СУБД, а не только в коде: на `coin_transactions` и
`audit_log` навешаны триггеры, отклоняющие `UPDATE` и `DELETE` (см.
[app/db/guards.py](app/db/guards.py)). Реализация есть для SQLite и PostgreSQL.

Поэтому ошибочная операция исправляется **обратной проводкой**, а не правкой
записи: возврат по заявке создаёт отдельную строку `purchase_refund`.

## Как считаются коины

Полный цикл соответствует п. 7 ТЗ.

```
показатели недели
   ↓ metric_definitions: value → баллы (доля выполнения плана × max_points)
базовые баллы
   ↓ антипоказатели: −(количество × штраф за единицу)
итоговый балл (не ниже нуля)
   ↓ ÷ курс (по умолчанию 5 баллов = 1 коин), округление вниз
базовые коины
   ↓ + место в топ-3, + неделя без опозданий, + неделя без сайтов, + номинации
коины за неделю
   ↓ close_week: проводки в журнал, зачисление на баланс
баланс оператора
```

Логика начисления баллов вынесена **в конфигурацию**, а не в код: каждый
показатель — строка `metric_definitions` с планом, весом и направлением
(«больше — лучше» / «меньше — лучше»). Руководитель меняет правила через
`PUT /api/v1/admin/config/rules` и `PATCH /api/v1/admin/config/metrics/{id}`
без релиза.

Значения по умолчанию (в сумме 100 баллов = 20 коинов за идеальную неделю):

| Показатель | План | Максимум баллов |
|---|---|---|
| Выработка часов | 40 ч | 25 |
| Переработки | 8 ч | 10 |
| Качество работы | 100 % | 25 |
| Эффективность | 100 % | 20 |
| Звонков в час | 12 | 15 |
| Благодарности от водителей | 5 | 5 |
| **Опоздания** (антипоказатель) | — | −5 за штуку |
| **Посторонние сайты** (антипоказатель) | — | −3 за штуку |

Бонусы (п. 3.2): 1-е место +15, 2-е +10, 3-е +7, неделя без опозданий +5,
неделя без посторонних сайтов +3, номинация +5, благодарность водителя +3.

### Идемпотентность

Каждое автоматическое начисление получает ключ вида
`week:{id}:user:{id}:points`. Повторный запуск закрытия недели — после сбоя,
перезапуска планировщика или ручного вызова — не начислит коины второй раз.
Закрытая неделя не пересчитывается: её правила зафиксированы в
`rules_snapshot`, так что изменение курса задним числом не переписывает историю.

## API

Все маршруты под префиксом `/api/v1`. Авторизация — `Authorization: Bearer <token>`.

### Аутентификация

| Метод | Путь | Описание |
|---|---|---|
| POST | `/auth/login` | вход по логину и паролю (form-data) |
| POST | `/auth/refresh` | обновление пары токенов |
| GET | `/auth/me` | профиль текущего пользователя |
| POST | `/auth/password` | смена собственного пароля |

### Личный кабинет оператора (п. 4.1)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/me/dashboard` | сводка: баланс, место, показатели недели, бейджи, номинации |
| GET | `/me/balance` | блок «Мой баланс» |
| GET | `/me/week` | показатели недели с прогресс-барами и ожидаемыми коинами |
| GET | `/me/transactions` | история с фильтрами `date_from`, `date_to`, `kind` |

| GET | `/me/levels` | лестница ступеней прогресса целиком |
| GET | `/me/shop-requests` | мои заявки из магазина |

### Формат ошибок

```json
{ "code": "insufficient_coins", "detail": "Недостаточно коинов: нужно 120, доступно 45. Не хватает 75.",
  "required": 120, "available": 45, "missing": 75 }
```

| Код HTTP | Когда |
|---|---|
| 400 | некорректный ввод: сумма сверх лимита, короткий комментарий, неизвестный оператор |
| 401 | нет или недействителен токен |
| 403 | роль или зона ответственности не позволяют операцию |
| 404 | объект не найден |
| 409 | конфликт состояния: неделя закрыта, заявка обработана, не хватает коинов |
| 422 | ошибка валидации схемы запроса |

## Роли и права

| Роль | Доступ |
|---|---|
| `operator` | только свой кабинет, рейтинг, магазин |
| `supervisor` | + админ-панель, ручные начисления и заявки **своих групп** |
| `head` | + все операторы, настройки правил и магазина, закрытие недели, полная история |
| `admin` | + управление учётными записями и сброс паролей |

Зона ответственности супервайзера — группы, где он указан как `supervisor_id`.
Попытка начислить коины оператору чужой группы возвращает 403.

Оператор в рейтинге видит место, ФИО, группу, баллы и коины за неделю коллег,
но **не видит их общий баланс** — это следует из требования п. 5 «чужие детали
скрыты». Поведение переключается настройкой `rating_show_balance_to_operators`;
персоналу баланс виден всегда.

## Автоматизация

Планировщик (APScheduler) по расписанию закрывает завершившуюся неделю:
считает баллы, места, номинации, начисляет коины и выдаёт бейджи.

```
SCHEDULER_ENABLED=true
WEEKLY_CLOSE_CRON_DAY_OF_WEEK=mon
WEEKLY_CLOSE_CRON_HOUR=3
```

По умолчанию — понедельник 03:00 по `TIMEZONE`. Ту же операцию можно выполнить
вручную через `POST /admin/weeks/{id}/close`; благодаря ключам идемпотентности
ручной и автоматический запуск не конфликтуют.

При горизонтальном масштабировании планировщик должен быть запущен ровно в одном
экземпляре — вынесите его отдельным процессом с `SCHEDULER_ENABLED=false`
на веб-подах.

## Тесты и качество

```bash
pytest -q          # 68 тестов
ruff check .       # линтер
```

Рабочие зависимости лежат в `requirements.txt`, инструменты разработки —
в `requirements-dev.txt`: в промышленный образ pytest и ruff не попадают.

Покрыты сценарии, где ошибка стоит дороже всего:

- **Расчёт баллов** — доли выполнения плана, потолок при перевыполнении,
  вычитание антипоказателей до перевода в коины, округление вниз.
- **Закрытие недели** — места и динамика, каждый бонус отдельной строкой истории,
  повторное закрытие не удваивает коины, закрытая неделя не пересчитывается.
- **Магазин** — резерв не меняет баланс, одобрение списывает, отказ возвращает,
  зарезервированные коины нельзя потратить дважды, цена фиксируется при подаче.
- **Журнал** — `balance_after` совпадает с накопительным итогом, `UPDATE` и
  `DELETE` отклоняются базой, ключ идемпотентности блокирует дубль.
- **Права** — оператор не попадает в админ-панель, супервайзер не меняет правила
  и не трогает чужую группу, чужой баланс скрыт в рейтинге.

## Развёртывание

### Render

В репозитории лежит [render.yaml](render.yaml) — Blueprint, который поднимает
API, PostgreSQL и статический сайт с интерфейсом одной кнопкой. Адрес API
интерфейс получает из соседнего сервиса, домены прописывать вручную не нужно.

1. Запушить репозиторий на GitHub или GitLab.
2. В Render: **New → Blueprint** → выбрать репозиторий → **Apply**.
3. Render спросит `BOOTSTRAP_ADMIN_PASSWORD` — задайте пароль администратора.
   `SECRET_KEY` он сгенерирует сам, `DATABASE_URL` подставит из созданной БД.
4. Через несколько минут сервис отвечает на `https://<имя>.onrender.com/health`,
   документация — на `/docs`.

Что происходит при деплое: `alembic upgrade head` раскатывает схему, затем
приложение при старте досоздаёт справочники (показатели, номинации, бейджи,
каталог магазина) и учётную запись администратора. Повторные деплои
идемпотентны — уже настроенные записи не перезаписываются.

Версия Python берётся из [.python-version](.python-version); `DATABASE_URL` от
Render приходит в формате `postgresql://…`, приложение само дописывает драйвер
`asyncpg` и переводит `sslmode` в понятный ему `ssl`.

#### Еженедельный расчёт на Render

На **free-плане веб-сервис засыпает** после 15 минут без трафика, поэтому
встроенный планировщик в понедельник 03:00 может не сработать. Варианты:

| Вариант | Как |
|---|---|
| Платный инстанс | сервис не засыпает — встроенный планировщик работает как есть |
| Render Cron Job | раскомментировать блок `cron` в `render.yaml`, у веб-сервиса выставить `SCHEDULER_ENABLED=false` (платно, от $1/мес) |
| Внешний планировщик | GitHub Actions или cron-job.org дёргает `POST /api/v1/admin/weeks/close-previous` токеном руководителя |

Команда `python -m scripts.close_week` делает то же самое из консоли и тоже
идемпотентна — повторный запуск не начислит коины дважды.

#### Ограничения free-плана

- Бесплатная база Render **удаляется через 30 дней** — для постоянной работы
  нужен платный план БД или регулярный дамп.
- Первый запрос после простоя занимает ~30 секунд (холодный старт).
- 512 МБ памяти и 0.1 CPU — для демонстрации и приёмки достаточно.

Демо-данные на Render можно налить разово из локальной консоли, подставив
внешнюю строку подключения:

```bash
DATABASE_URL="<External Database URL из Render>" python -m scripts.seed_demo
```

### PostgreSQL + Docker

```bash
SECRET_KEY=$(python -c "import secrets; print(secrets.token_hex(32))") \
  docker compose up --build
```

Compose поднимает PostgreSQL, прогоняет `alembic upgrade head` и стартует API
на порту 8000.

### Миграции

```bash
alembic upgrade head                              # применить
alembic revision --autogenerate -m "описание"     # создать новую
alembic downgrade -1                              # откатить
```

В промышленной среде выключите `AUTO_CREATE_SCHEMA` — схемой управляет Alembic.
`SEED_REFERENCE_DATA` можно оставить включённым: справочники досоздаются
идемпотентно, уже настроенные записи не трогаются.

### Перед выходом в прод

- [ ] заменить `SECRET_KEY` и `BOOTSTRAP_ADMIN_PASSWORD`
- [ ] перевести `DATABASE_URL` на PostgreSQL
- [ ] `AUTO_CREATE_SCHEMA=false`, схему раскатывать миграциями
- [ ] сузить `CORS_ORIGINS` до доменов фронтенда
- [ ] запустить планировщик ровно в одном экземпляре
- [ ] выдать приложению роль БД без `UPDATE`/`DELETE` на журналах — второй рубеж
      защиты истории в дополнение к триггерам

## Принятые решения и допущения

ТЗ оставляет несколько мест на усмотрение разработки. Решения ниже стоит
подтвердить с заказчиком.

1. **Формула баллов конкурса.** П. 3.1 ссылается на «существующие правила
   Байга ОТП», которых нет в документе. Реализован настраиваемый движок: план,
   максимум баллов и направление задаются на каждый показатель, значения по
   умолчанию дают 100 баллов за идеальную неделю. Перенос реальных весов —
   это правка справочника, не кода.

2. **Округление при переводе баллов.** Округление вниз: сумма начислений никогда
   не превышает заработанное. Остаток баллов не переносится на следующую неделю.

3. **Дисциплинарные бонусы при отсутствии данных.** Если антипоказатель за неделю
   не выгружен, бонус «без опозданий» **не** начисляется: отсутствие строки — это
   «данных нет», а не «нарушений не было». Управляется настройкой
   `discipline_requires_reported`.

4. **Кто участвует в рейтинге.** Только операторы, по которым за неделю есть хотя
   бы один показатель. Сотрудник в отпуске не попадает в конец таблицы с нулём.

5. **Равные баллы.** Спортивное ранжирование: 1, 2, 2, 4. Оба вторых места
   получают полный бонус за второе место.

6. **Чужой баланс в рейтинге.** П. 4.2.4 требует колонку «общий баланс», п. 5
   требует скрывать чужие детали. Компромисс: операторам чужой баланс скрыт,
   персоналу виден, поведение переключается настройкой.

7. **Номинации при малом числе участников.** Не присуждаются, если участников
   меньше `nomination_min_participants` (по умолчанию 3), иначе победителем
   становится единственный участник.

8. **Резерв коинов.** Заявка резервирует коины, не меняя баланс: оператор видит
   и баланс, и сколько из него уже обещано магазину. Списание происходит только
   при одобрении.

9. **Цена бонуса фиксируется при подаче заявки.** Изменение прайса не влияет на
   уже поданные заявки.

10. **Лимит на ручную операцию** — 100 коинов за раз (`manual_max_abs_amount`),
    чтобы опечатка не сломала экономику. Комментарий обязателен, минимум 5 символов.

11. **Поиск по ФИО на SQLite** регистрозависим для кириллицы — ограничение
    `LIKE` в SQLite. На PostgreSQL `ILIKE` работает корректно.

## Уровни прогресса

Реализована первая позиция второй очереди (п. 6.2 ТЗ): Новичок → Профи →
Эксперт → Легенда.

Ступень **нигде не хранится** — она вычисляется от `total_earned`, суммы всех
начислений за всё время. Отсюда два следствия:

- **трата коинов не понижает уровень**: оператор не выбирает между наградой
  и статусом;
- **изменение порога применяется сразу ко всем** — руководителю не нужен
  пересчёт, достаточно `PATCH /admin/config/levels/{id}`.

Пороги по умолчанию: 0 / 150 / 400 / 1000 накопленных коинов. Ступень видна
в кабинете под балансом и полной лестницей в профиле, где у недостигнутых
показан порог.

## Что не входит в MVP

Вторая очередь по п. 6.2 ТЗ — не реализовано:

- push- и email-уведомления;
- график динамики за 4–8 недель;
- автоматические розыгрыши среди купивших билеты;
- сезонные магазины и временные лоты;
- расширенная аналитика для руководителя;
- мобильное приложение.

Задел под них уже есть: `total_earned` на счёте (уровни), `operator_week_results`
по неделям (графики), `shop_requests` по позиции `raffle_ticket` (розыгрыши),
`stock_limit` и `is_active` у бонуса (сезонные лоты).
