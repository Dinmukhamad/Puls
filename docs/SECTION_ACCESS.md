# Доступ к разделам Puls

Уточнение пользователя от 06.09.2026 заменяет фиксированное количество разделов:
состав меню определяется рабочими задачами роли и назначенными разрешениями.

## Настройка в интерфейсе

Администратор открывает **Система → Доступ к разделам** (`/admin/access`).

1. Выбирает получателей: все сотрудники, одна или несколько ролей, групп либо аккаунтов.
2. Для нужных разделов выбирает «Разрешить», «Запретить» или «Наследовать».
   «Не менять» сохраняет текущее правило. Выбор получателей сохраняется при поиске
   и переключении страниц; до 200 получателей за одно сохранение.
3. Проверяет список подготовленных изменений и нажимает «Применить права».
4. В блоке «Проверить доступ сотрудника» видит итоговые разрешения и источник каждого.

Приоритет: аккаунт → группа сотрудника → роль → все сотрудники → настройки по умолчанию.
На одном уровне существует одно правило для пары получатель/раздел. «Наследовать»
удаляет это правило; более конкретные исключения сохраняются. Общее правило
распространяется и на будущие аккаунты. Смена роли/группы автоматически меняет наследование.

## Разделы по умолчанию

| Область | Оператор | Супервайзер | Руководитель | Администратор |
| --- | --- | --- | --- | --- |
| Личный кабинет, XP и кошелёк | Да | Нет | Нет | Нет |
| Рейтинг и результаты | Да | Да | Да | Да |
| Прохождение обучения | Да | Нет | Нет | Нет |
| Личный магазин и игры | Да | Нет | Нет | Нет |
| Сводка, команда, аналитика, расчёт периодов | Нет | Да | Да | Да |
| Управление обучением и мотивацией | Нет | Да | Да | Да |
| Отчёты и CSV | Нет | Нет | Да | Да |
| Полный аудит | Нет | Нет | Нет | Да |
| Сессии и устройства | Нет | Нет | Нет | Только аккаунт разработчика |
| Управление правами | Нет | Нет | Нет | Всегда |
| Профиль, пароль, уведомления | Всегда | Всегда | Всегда | Всегда |

Главная управленческого аккаунта — сводка. Личные XP, коины, игры, покупки и
прохождение обучения появляются после отдельного разрешения. Пустые контейнеры
меню удаляются. Если остался только рейтинг внутри производительности/мотивации,
пункт называется «Результаты». При закрытой главной корневой адрес открывает
первый доступный раздел, а при отсутствии рабочих разделов — профиль.

## Границы разрешений

Разрешение даёт доступ к разделу и его просмотру. Возможность изменять данные
остаётся привязанной к рабочей роли: например, оператор с доступом к периодам
может читать доступные результаты, но не импортировать и не публиковать их.
Руководитель с закрытым разделом не может ни читать, ни изменять его данные.

Область сотрудников сохраняется: оператор — собственные данные; супервайзер —
свои подчинённые группы и себя; руководитель/администратор — организация.
Каталог учебных материалов, правила расчёта, товары и игры — общие справочники
соответствующего разрешённого раздела. Для фильтров и выбора получателей есть
отдельные ограниченные справочники `/lookups/users` и `/lookups/groups` без
логинов, email и финансовых данных. Мотивация также использует определения
метрик и правила коинов как вспомогательные справочники.

Полный аудит и управление правами остаются административными возможностями.
Разрешение системного раздела для общего правила/группы
применяется только к администраторам; повысить роль таким правилом нельзя.
Управление правами нельзя закрыть самому администратору через эту матрицу.

**Уточнение владельца: сессии и устройства доступны только разработчику.**
Единственная точка входа — «Система → Сессии и устройства» (`/admin/sessions`).
В профиле нет ссылок или вкладок устройств. Прежний `/sessions` перенаправляет
разработчика на общий экран; другим аккаунтам доступ закрыт. В едином экране
можно переключаться между всеми аккаунтами и своими сеансами.

Разработчик определяется серверной настройкой `DEVELOPER_LOGIN` и ролью `admin`.
Для текущей установки используется логин `admin`, показанный владельцем на скриншоте.
Другие аккаунты с ролью администратора эту возможность не получают. Настройка
не редактируется через интерфейс, матрица разделов её не выдаёт; пустое значение
отключает доступ. Все `/me/sessions*` и `/admin/sessions*` проверяют разработчика,
включая чтение и завершение сеансов. API запрещает другим администраторам менять,
отключать или сбрасывать пароль аккаунта разработчика и создавать аккаунт с его
зарезервированным логином. Самостоятельная смена пароля и выход доступны каждому;
автоматический отзыв прежних токенов при смене пароля сохраняется.

Сервер проверяет разрешение при каждом запросе. Интерфейс обновляет его при
возврате в окно, раз в 30 секунд и после ответа `section_denied`/`developer_required`. Изменение
доступа или области данных очищает старые запросы и кеш представлений.
Кнопки перехода, быстрые действия, профиль, вкладки карточки сотрудника и
страницы отчётов учитывают доступ. Проверка действует и по прямому адресу.

Каждое изменение записывается в аудит с автором, получателями, прежними и новыми
правилами. Массовое сохранение атомарно; устаревшая версия правил даёт `409`,
чтобы два администратора не перезаписали изменения друг друга незаметно.

## Установка и проверка

Перед запуском API выполнить `alembic upgrade head`. Миграция `20260906_access`
добавляет только таблицы правил и версии политики; аккаунты и история сохраняются.
Render уже выполняет миграции в команде запуска. После обновления фронтенд
получает права от API, а не назначает разрешения из локальной роли.

Автотесты проверяют матрицу ролей, приоритеты, массовые операции, наследование,
ограничение данных, запрет изменений при делегированном просмотре, прямые
адреса, параллельное сохранение, защищённый доступ администратора и состав меню.
Визуальная проверка в живом браузере остаётся открытой: подключённых браузеров нет.
