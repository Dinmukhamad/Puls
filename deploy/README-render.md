# Деплой Puls на Render (бесплатно, без карты)

Render разворачивает приложение прямо из GitHub-репозитория — как Railway.
База — отдельно (рекомендуется Neon; можно и Postgres самого Render).

> **Render деплоит то, что лежит в GitHub, а не то, что у вас на диске.**
> Перед деплоем закоммитьте и отправьте изменения в `main`. Если правили
> фронтенд — сначала `npm run build`: на сервере сборка не выполняется,
> Render отдаёт уже собранные бандлы из репозитория.

> **Минус бесплатного тарифа:** веб-сервис «засыпает» после ~15 минут без
> запросов, первый заход будит его 30–60 секунд. Плюс автоматический
> еженедельный расчёт коинов (APScheduler) на спящем сервисе может не
> сработать вовремя — на бесплатном тарифе расчёт надёжнее запускать вручную
> из админки. Об этом — в конце.

---

## 1. Создать базу данных

### Вариант A — Neon (рекомендуется)
1. Регистрация на https://neon.tech (карта не нужна).
2. Create Project → регион поближе.
3. Скопируйте **Connection string** вида
   `postgresql://user:pass@ep-xxx.neon.tech/dbname?sslmode=require`.
   Это будет `DATABASE_URL`.

### Вариант B — Postgres от Render
1. В Render: **New → Postgres** (Free).
2. После создания скопируйте **Internal Database URL**.
   ⚠️ Бесплатная база Render со временем удаляется по неактивности —
   для долгого использования надёжнее Neon.

---

## 2. Создать веб-сервис

1. Render → **New → Web Service** → подключите репозиторий
   `Dinmukhamad/Puls` (авторизуйте GitHub при первом разе).
2. Настройки:
   - **Runtime:** `Python 3`
   - **Build Command:**
     ```
     pip install -r requirements.txt
     ```
   - **Start Command:**
     ```
     bash start.sh
     ```
     (start.sh сам применит миграции `alembic upgrade head`, затем запустит
     uvicorn на порту `$PORT`, который Render задаёт автоматически.)
   - **Instance Type:** Free
   - **Health Check Path:** `/ready`

**Не меняйте Start Command.** `start.sh` применяет миграции и поднимает uvicorn
ровно в один рабочий процесс (`--workers 1`). Один процесс — обязательное
условие: кеши рейтинга и аналитики процесс-локальные, и при двух воркерах
второй продолжал бы отдавать устаревшие цифры после загрузки новых отчётов
(подробности — в комментарии внутри `start.sh`).

Имя сервиса задаёте вы — из него складывается адрес
`https://<имя-сервиса>.onrender.com`. Запишите его: понадобится на шаге 3.

> **Альтернатива — через Docker.** В репозитории уже есть `Dockerfile`.
> Тогда Runtime выберите **Docker**, Build/Start Command не нужны — Render
> соберёт по Dockerfile. Но для Render проще нативный Python (выше).

---

## 3. Переменные окружения

⚠️ **Все переменные ниже обязательны.** Render сам выставляет `RENDER=true`,
и по этому признаку срабатывает `check_production_safety()` — приложение
**откажется стартовать**, если хоть одна небезопасная настройка осталась.
Пропуск любой строки из таблицы = crash loop при первом же деплое.

В настройках сервиса → **Environment** → добавьте:

| Ключ                  | Значение                                            | Зачем |
|-----------------------|-----------------------------------------------------|-------|
| `DATABASE_URL`        | строка подключения из шага 1                         | SQLite в production запрещён |
| `JWT_SECRET_KEY`      | секрет ≥ 32 символов (`openssl rand -hex 32`)        | подпись сессий |
| `APP_ENV`             | `production`                                         | режим работы |
| `SEED_ADMIN_PASSWORD` | пароль первого администратора                         | создаётся при первом старте |
| `SEED_ADMIN_USERNAME` | `admin` (по желанию)                                 | логин администратора |
| `CORS_ORIGINS`        | `https://ваш-сервис.onrender.com` — **не `*`**        | при cookie-авторизации `*` небезопасен |
| `AUTH_COOKIE_SECURE`  | `true`                                               | Render отдаёт HTTPS, кука только по нему |
| `AUTO_CREATE_TABLES`  | `false`                                              | схему создаёт только Alembic |
| `ENABLE_DEMO_DATA`    | `false`                                              | демо-операторы не нужны на проде |
| `CSRF_ENFORCED`       | `true`                                               | фронтенд шлёт `X-CSRF-Token`, защита работает |
| `TRUST_FORWARDED_FOR` | `true`                                               | Render — за прокси; иначе все входы видны с одного IP |
| `PYTHON_VERSION`      | `3.13.1`                                             | проект на Python 3.13 |
| `RELEASE_ID`          | любая метка, например `2026-08-30-1` (по желанию)     | видно в `/health`, помогает опознать деплой |

### Про `CORS_ORIGINS` и «курицу с яйцом»

Точный адрес сервиса известен только после его создания. Порядок такой:
имя сервиса вы задаёте сами при создании, адрес складывается как
`https://<имя-сервиса>.onrender.com` — впишите его сразу. Если ошиблись,
поправьте переменную после первого деплоя: Render передеплоит автоматически.

### Про `TRUST_FORWARDED_FOR`

На Render приложение всегда стоит за платформенным прокси, поэтому реальный
IP приходит в заголовке `X-Forwarded-For`. Без этого флага все запросы
выглядят как один клиент: защита логина от перебора начнёт считать попытки
всех сотрудников в общую корзину, а в журнале сессий у всех будет один адрес.

## 4. Запустить

Нажмите **Create Web Service** и откройте вкладку **Logs**. Порядок запуска
(см. `start.sh` и `app/core/lifespan.py`):

1. **Проверка безопасности** — сверяются переменные из шага 3. При проблеме
   падает сразу, до обращения к базе.
2. **Миграции** — `alembic upgrade head` создаёт и обновляет все таблицы.
3. **Совместимость схемы** и закрытие зависших попыток миссий.
4. **Наполнение справочников** — уровни, Колесо WOW, достижения, магазин,
   экономика коинов, миссии, учётная запись администратора. Операция
   идемпотентна: при рестарте ничего не задваивается.
5. **Запуск uvicorn** на порту `$PORT`, который Render задаёт автоматически.

Успешный лог выглядит так:

```
[start] Running alembic upgrade head...
[start] Migrations complete
[startup] Schema compatibility OK
[startup] Seed OK
INFO:     Uvicorn running on http://0.0.0.0:10000
INFO:     Application startup complete.
```

Когда Render пометит сервис **Live**, а `/ready` вернёт 200 — приложение работает.

Откройте выданный адрес `https://ваш-сервис.onrender.com` — должно открыться
приложение. Вход: `admin` + пароль из `SEED_ADMIN_PASSWORD`.

После первого успешного входа **удалите `SEED_ADMIN_PASSWORD`** из
Environment (или смените пароль в интерфейсе) — иначе пароль администратора
остаётся лежать открытым текстом в настройках сервиса.

### Если деплой падает

Откройте **Logs** и найдите строку, начинающуюся с `FATAL:`.

```
RuntimeError: FATAL: unsafe production configuration: <перечень проблем>
```

Это не сбой платформы, а намеренная защита: приложение отказывается стартовать
с небезопасными настройками. Каждая фраза в перечне указывает на конкретную
пропущенную переменную из таблицы шага 3:

| Строка в логе | Что добавить |
|---|---|
| `CORS_ORIGINS must be explicit in production` | `CORS_ORIGINS=https://ваш-сервис.onrender.com` |
| `AUTO_CREATE_TABLES must be false in production` | `AUTO_CREATE_TABLES=false` |
| `ENABLE_DEMO_DATA must be false in production` | `ENABLE_DEMO_DATA=false` |
| `CSRF_ENFORCED must be true in production` | `CSRF_ENFORCED=true` |
| `AUTH_COOKIE_SECURE must be true in production` | `AUTH_COOKIE_SECURE=true` |
| `JWT_SECRET_KEY must be a non-default secret…` | секрет ≥ 32 символов, не из примеров |
| `DATABASE_URL must point to PostgreSQL` | строка подключения из шага 1 |

Другие частые случаи:

- **`/ready` отдаёт 503, сервис помечен нездоровым.** Значит база отвечает, но
  схема не соответствует коду. Проверьте в логах, что `alembic upgrade head`
  отработал без ошибок до запуска uvicorn.
- **Вход не проходит, в консоли браузера 403 «Недействительный CSRF-токен».**
  Проверьте, что `CORS_ORIGINS` содержит именно тот адрес, по которому вы
  открыли сайт (с `https://`, без слэша в конце).

---

## 5. Обновления

Render **сам передеплоит** при каждом push в `main` (auto-deploy включён по
умолчанию). Ручной передеплой — кнопка **Manual Deploy → Deploy latest commit**.

---

## 6. Про «засыпание» и еженедельный расчёт

- **Холодный старт.** Чтобы сервис не засыпал, можно раз в ~10 минут пинговать
  его healthcheck. Бесплатный способ — внешний пинг-сервис (например,
  cron-job.org) с адресом `https://ваш-сервис.onrender.com/health`.
  ⚠️ Это обходит «сон», но расходует бесплатные часы Render быстрее.
- **Еженедельный расчёт коинов.** Встроенный планировщик (APScheduler)
  запускает расчёт по понедельникам в 09:00 Asia/Almaty, но на спящем сервисе
  задача просто не выполнится. На бесплатном тарифе надёжнее **запускать
  расчёт периода вручную** из админки (раздел «Расчёт периода»). Двойного
  начисления не будет: уникальность `(operator_id, period_start, period_end)`
  в `weekly_accrual_details` не даст провести начисление дважды, даже если
  планировщик отработает следом.
- **Загруженные Excel-файлы переживают редеплой.** Monthly Report и Report
  хранятся в БД (`uploaded_report_files.content`), а не на диске. Это важно
  именно на Render: файловая система там временная и очищается при деплое.
  Отдельный persistent disk подключать не нужно.

## Итог
Neon (база) + Render (приложение), деплой из того же репозитория, миграции
применяются сами. С «сном» и ручным еженедельным расчётом придётся мириться —
для внутреннего инструмента это терпимо. Если позже возьмёте платный план
Render (~$7/мес) — сервис перестанет засыпать и планировщик заработает штатно.
